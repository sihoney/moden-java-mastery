Java 8 이후부터 도입된 **CAS(Compare-And-Swap)**는 "일단 락을 걸고 보는" 방식이 아니라, **"일단 시도하고, 값이 바뀌었으면 다시 한다"**는 아주 낙천적인(Optimistic) 방식입니다.

동작 원리를 쉽게 설명해 드릴게요.

---

### 1. CAS의 핵심 원리

CAS는 3가지 요소를 가지고 동작합니다.

1. **메모리 위치 (V):** 값을 읽어올 실제 주소
2. **기대값 (A):** 내가 읽었을 때의 값
3. **새로운 값 (B):** 내가 바꾸고 싶은 값

**작동 순서:**

* 쓰레드가 데이터를 수정하기 전, 현재 값을 읽어 **기대값(A)**으로 저장합니다.
* 계산을 마친 후, 값을 쓰려고 할 때 **현재 메모리(V)에 있는 값**이 내가 처음에 읽었던 **기대값(A)**과 일치하는지 확인합니다.
* **일치하면:** 아무도 건드리지 않았다는 뜻이므로 **새로운 값(B)**으로 교체합니다. (성공)
* **일치하지 않으면:** 그 사이 다른 쓰레드가 값을 바꿨다는 뜻이므로, 처음부터 다시 시도합니다. (실패 및 재시도)

### 2. ConcurrentHashMap에서의 활용

`ConcurrentHashMap`은 새로운 노드를 삽입할 때 이 CAS를 사용합니다.

* **비어있는 버킷일 때:** 굳이 무거운 락(`synchronized`)을 걸 필요가 없습니다. CAS를 이용해 "이 칸이 비어있다면 내 노드를 넣어라"라고 시도합니다. 성공하면 락 없이 바로 작업이 끝납니다.
* **이미 데이터가 있을 때:** 이때는 충돌 가능성이 높으므로 해당 버킷의 첫 번째 노드에 `synchronized`를 걸어 안전하게 데이터를 추가(Link)합니다.

---

### 3. 왜 이렇게 하나요? (장단점)

| 특징 | 설명 |
| --- | --- |
| **낮은 비용** | 하드웨어(CPU) 차원에서 지원하는 원자적 연산이라 `synchronized`보다 훨씬 빠릅니다. |
| **Non-blocking** | 특정 쓰레드가 락을 잡고 놓아주지 않아 다른 쓰레드들이 무한정 대기하는 상황을 방지합니다. |
| **단점 (Busy-wait)** | 충돌이 너무 잦으면 계속 재시도(Loop)를 해야 하므로 오히려 CPU 점유율이 높아질 수 있습니다. |

### 요약하자면

`ConcurrentHashMap`은 **"비어있을 땐 가벼운 CAS로, 복잡할 땐 확실한 락으로"** 처리하는 하이브리드 전략을 사용합니다. 덕분에 Java 7의 세그먼트 방식보다 훨씬 세밀하고 빠른 성능을 낼 수 있는 것이죠.
