# 🧪 Week 1 — Learning Log

## Lab 01 — Modern Java Type Design

### 1. Sealed + Record 설계 감각

* `record`는 불변 데이터 모델링의 기본 단위다.
* `sealed interface`는 도메인에서 허용되는 행위를 **컴파일 타임에 봉인**한다.
* 생성자에서 검증을 수행하면 **잘못된 상태의 객체가 시스템에 들어올 수 없다.**
* 데이터 무결성이 코드 구조로 보장된다.

### 느낀 점

> 입력 검증을 로직이 아니라 **타입 생성 시점**에 둔 순간,
> 전체 코드가 훨씬 단순해졌다.

## Lab 02 — Real CLI System with Picocli

### 2. 문자열 → 타입 변환 파이프라인

```
사용자 입력 → Picocli → Command 객체 → Service → Persistence
```

* CLI 입력은 더 이상 문자열이 아니다.
* Picocli는 파싱, 검증, 에러 메시지, 도움말 생성을 전부 처리한다.
* 우리는 오직 **도메인 로직만 작성**한다.

### 느낀 점

> 이 구조는 서버의 Controller → DTO → Service 구조와 완전히 동일하다.

## Lab 03 — Concurrency Reality Check

### 3. synchronized 실험

* `synchronized`는 **안전하지만 확장성이 없다.**
* 제거 시 race condition 발생:

    * ID 불일치
    * 파일 상태 붕괴
    * 데이터 중복
* 가장 무서운 점:
  **에러 없이 데이터가 조용히 깨진다.**

### 느낀 점

> 동시성 버그는 대부분 “조용한 데이터 부패”로 나타난다.

## Lab 04 — Structural Concurrency Design

### 4. 구조로 동시성을 해결

기존:

```
synchronized handle()
  ├─ ID 생성
  ├─ 상태 변경
  └─ 파일 저장
```

개선:

```
NoteRepository → 상태
FileWriterWorker → IO
NoteService → 흐름
```

* `ConcurrentHashMap`으로 상태 보호
* IO를 비동기로 분리
* 충돌 자체를 설계에서 제거

### 느낀 점

> 동시성은 **락 기술이 아니라 설계 문제**다.

---

## 비동기 시스템 핵심 통찰

### 5. 왜 재시도와 관측이 필수인가

* 비동기는 “나중에 처리한다”는 약속이다.
* 실패는 조용히 발생한다.
* 재시도가 없으면 **일시 장애 = 데이터 유실**
* 관측이 없으면 **장애가 존재하지 않는 것처럼 보인다**

### 느낀 점

> 비동기는 성능을 얻는 대신,
> **신뢰를 설계로 다시 사는 구조**다.

---

## Executor & JVM 생명주기

### 6. Executor가 JVM을 붙잡는 이유

* Executor 스레드는 **non-daemon**
* non-daemon 스레드가 하나라도 살아 있으면 JVM은 종료되지 않는다.
* 따라서 반드시 `shutdown()`으로 생명주기를 관리해야 한다.

### 느낀 점

> 스레드 풀, 커넥션 풀, 메시지 큐는
> 모두 **시스템 생명주기의 일부**다.

## 최종 요약 — Week 1에서 얻은 감각

* 현대 Java는 **타입으로 시스템을 설계**한다.

* 시스템 신뢰성은 **재시도 + 관측**으로 확보한다.
* JVM 생명주기는 **자원 관리 설계의 일부**다.
