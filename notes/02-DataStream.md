아주 핵심 질문이다.
여기 이해하면 **대용량 시스템 설계의 감각**이 생긴다.

지금 네가 물은 세 가지는 사실 하나의 원리에서 나온다:

> **“데이터를 쌓지 말고, 흘려보내라.”**

아래에서 아주 물리적으로 설명할게.

---

# 🧠 1. 왜 GC가 폭주하지 않는가

GC(Garbage Collection)가 폭주하는 상황은 딱 하나다:

> **메모리에 객체가 너무 많이 쌓일 때**

전통적인 방식:

```java
List<String> lines = Files.readAllLines(path);
```

이 코드는:

* 파일 전체를 한 번에 메모리에 적재
* 수백만 개의 String 객체 생성
* 힙이 가득 찬다
* GC가 미친 듯이 돌기 시작한다

이 상태가 **GC 폭주**다.

---

지금 방식:

```java
try (Stream<String> s = Files.lines(path)) {
    s.map(...).filter(...).forEach(...);
}
```

이 구조는:

* 한 줄 읽음 → 처리 → 버림
* 다음 줄 읽음 → 처리 → 버림
* **메모리에 쌓이지 않는다**

즉, 힙이 계속 작게 유지된다.
그래서 GC가 거의 할 일이 없다.

> **객체가 힙에 오래 머물지 않으니 GC도 바쁘지 않다.**

---

# 🧨 2. 왜 OOM(Out Of Memory)이 방지되는가

OOM은 단순하다:

> **힙이 꽉 차면 발생**

`readAllLines()` 방식은 파일 크기만큼 힙을 요구한다.
10GB 파일이면 → 10GB 메모리 필요 → 대부분의 서버는 즉시 OOM.

지금 방식은:

* 메모리에 항상 **몇 줄 분량만 존재**
* 힙 사용량이 거의 일정
* 파일 크기와 무관

그래서:

> **파일이 아무리 커도 메모리가 터지지 않는다.**

---

# 🌊 3. 백프레셔란 무엇인가

**Backpressure**는 직역하면 “뒤에서 누르는 압력”이다.

시스템적으로는:

> **소비 속도가 생산 속도를 제어하는 현상**

지금 구조를 보면:

```
파일 읽기 → 파싱 → 분석
```

이게 하나의 파이프라인이다.

파일 읽기는 **분석이 끝나야** 다음 줄을 읽는다.
분석이 느리면 → 파일 읽기도 느려진다.

즉:

> **처리 속도가 읽기 속도를 자동으로 제한한다**

이게 **자연 발생적 백프레셔**다.

반대로 `readAllLines()`는:

```
파일 전체 읽기 → (메모리에 적재) → 처리
```

처리 속도와 상관없이 **무조건 다 읽는다**
그래서 메모리가 터진다.
