아주 핵심 질문이다.
이 질문에 답이 들어오면 **“동시성”이 기술이 아니라 설계 문제**라는 게 딱 보이기 시작한다.

결론부터 말하면 이거다:

> **`synchronized`는 “문 잠그기”이고,
> 자료구조 + 책임 분리는 “교통 체계 만들기”다.**

문 잠그는 방식은 안전하지만, **도시는 절대 커지지 않는다.**

---

## 🧱 `synchronized`가 가진 구조적 한계

`synchronized`는 이렇게 말한다:

> “이 객체에 접근하는 사람은 **한 명씩 줄 서라**”

문제는 이거다:

* CPU 코어는 8개, 16개인데
* 프로그램은 **1명만 일함**
* 나머지는 **기다리기만 함**

즉, **성능을 포기하고 안정성을 산다.**

작은 실험에서는 괜찮다.
**시스템이 되면 바로 병목**이다.

## 🧬 자료구조로 해결하면 뭐가 달라질까

### 1️⃣ ConcurrentHashMap이 해주는 일

`ConcurrentHashMap`은 내부에서:

* 영역을 쪼개고
* 각 영역에 다른 락을 걸고
* 읽기는 대부분 lock-free로 처리한다

그래서:

| 상황         | synchronized | Concurrent 구조 |
| ---------- | ------------ | ------------- |
| 10개 스레드 쓰기 | 직렬 처리        | 병렬 처리         |
| 읽기 1000번   | 대기열          | 거의 락 없음       |
| 확장성        | 급격히 붕괴       | 자연스럽게 증가      |

---

### 2️⃣ 책임 분리는 충돌 자체를 줄인다

우리는 이렇게 나눴다:

```
NoteRepository → 메모리 상태
FileWriterWorker → 디스크 IO
NoteService → 흐름 조정
```

이게 왜 중요한가?

이전 구조는:

```
handle() 안에서
  상태 수정
  ID 생성
  파일 저장
```

→ **모든 위험 요소가 한 임계 구역에 몰림**

지금 구조는:

```
상태 변경 (빠름, 메모리)
↓
IO 작업 (느림, 분리)
```

→ **충돌 가능성 자체가 사라짐**

## 🧠 동시성의 본질

동시성은
**"누가 먼저 실행되느냐"**의 문제가 아니라

> **“서로 충돌하지 않게 구조를 어떻게 설계하느냐”**

의 문제다.
